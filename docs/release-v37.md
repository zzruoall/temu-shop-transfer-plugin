## 弹性分配

只按有就绪任务的账户分配资源。人数少时同一账户可借用空闲名额处理不同店铺；竞争时优先向占用较少的就绪账户分配释放的名额。已执行任务不会为重新分配而被强杀。

当前保守硬上限为业务2、单账户2、准备进程1、未决平台许可2。启动先给1个业务名额，持续健康后逐步增长；资源压力或采样失效会阻止新准入。未知结果保留占位和证据，不按超时强制重投。多个店铺不代表每个准备步骤都会并行。

| 环境变量 | 本次生产值 |
| --- | --- |
| `ZINIAO_ACCOUNT_PROCESS_MODE` | `on` |
| `ZINIAO_ELASTIC_MODE` | `on` |
| `ZINIAO_ELASTIC_BUSINESS_MAX` | `2` |
| `ZINIAO_ELASTIC_ACCOUNT_MAX` | `2` |
| `ZINIAO_ELASTIC_PROCESS_MAX` | `1` |
| `ZINIAO_ELASTIC_PUBLISH_MAX` | `2` |

配置不是迁移替代品。启用前要在隔离环境验证数据库模式，备份并排空在途工作，停服后执行相应显式离线迁移。弹性增量入口为 `hub/scripts/migrate-elastic-allocation.mjs --confirm-offline`，它依赖账户执行模式的既有表；不要跳过基础迁移直接启用开关。有活动弹性槽时不能直接回退旧模式或恢复旧SQL覆盖新回执。

## 验证范围

发布前完成资源策略、隔离 MySQL 和真实 worker/模拟插件链测试；在 Linux 的768MiB/0.6核限制下验证额度增长。上线后公网接口和资产哈希通过，同一生产实例观察到1到2增长。真实平台业务测试尚需用户进行，未声称最大吞吐或上百账户同时执行已经测定。
